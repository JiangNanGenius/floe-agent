# 建筑项目：资料整理、房间信息与 AI 输入设计

创建日期：2026-11-12；需求更新：2026-11-13。状态：需求与技术设计；2026-11-13 已开始独立 GRDB 资料／料单组件和工作台实现，原生编译与宿主验收分别记录。本文描述的完整范围尚未全部实现。依据为[已确认的 28 项 QA](FLOE_BUILDING_EDITOR_REQUIREMENTS_QA_20261112.zh-CN.md)，以及用户追加的要求：通过项目 AI 助手提供手绘、零散房间资料，必须妥善整理、持久记录，便于 AI 查找和高效利用；新增智能家居／暖通专属工作台、智能家居料单导入和 AI 整理导入文件的明确能力。本文的具体结构是设计方案，不冒充额外选择题的用户答案。

后续用户已明确需要内部表单／小数据库，并保留 Floe 自有二维／三维核心，寻找成熟的中间层和资产来源。本方案已进一步具体化为 SQLite／现有 GRDB、8 类表单定义和可执行 SQL 设计原型，详见[实施蓝图](FLOE_BUILDING_EDITOR_CORE_REUSE_AND_DATA_BLUEPRINT_20261112.zh-CN.md)。原型的数据检查不等于原生 App 集成。

默认工作流进一步按室内装修组织。房间资料、量尺校正、现状／拆改决定、饰面、柜体与五金规则都要能定位到相关施工图和部件明细，见[图纸与柜体深化方案](FLOE_INTERIOR_DRAWINGS_AND_CABINET_DETAILING_20261112.zh-CN.md)。原生视图／标注仍由 CAD 文档保存，数据库保留来源和对应，不重复维护另一份图纸。

## 一、用户提供资料后的完整操作

目标操作：用户把手绘户型、几张现场照片、零散尺寸说明及量尺结果交给当前建筑项目，AI 整理成可以查看、追溯、修改并用于建模的项目资料。

1. **接收并归档。** 保留原图／原文件；项目内的文字补充保存成有来源的记录。普通聊天中提供的资料，只有明确关联到此项目后才进入该项目，不能依赖临时附件路径或跨项目猜测归属。
2. **提取并归类。** 识别文字、尺寸、房间名称、门窗及相邻关系，关联到楼栋、楼层、房间或构件。不能确定归属的内容进入“待整理”，保留问题，不随意挂到第一个房间。
3. **形成房间信息。** 将尺寸、层高、门窗、现场条件、家具／柜体需求、饰面及设计限制汇总成可编辑的信息表。每个值仍能打开对应原文、图片区域或测量记录。
4. **处理缺失与矛盾。** 明确的用户输入可以直接整理；只对影响当前操作的关键歧义、缺失和冲突提问。原资料与模型不同，不等于每次都要重新向用户确认全部资料。
5. **生成或修改模型。** 在已授权的建模任务内，通过同一原生编辑会话创建可编辑构件并记录版本。提取、推断、用户确认与模型应用是可区分的状态；建模失败不会删除资料。
6. **持续更新。** 后续补充一张图、一条尺寸或一次扫描，可以定位受影响的房间、构件和结果，比较并局部更新。已解决的问题不因助手重开而再次询问。

界面反馈应是“已整理到一层厨房，发现一处尺寸冲突”等直接结果。存储格式、索引、协议及内部标识留在诊断或开发文档中。

## 二、项目里分别记录什么

| 内容 | 保存内容 | 在建模中的作用 |
| --- | --- | --- |
| 原始资料 | 手绘、图片、PDF、导入图纸、扫描文件、文字补充；原文件名、导入时间及来源版本 | 可追溯依据，识别失败也保留 |
| 提取与测量记录 | 文字片段、尺寸原文／单位／标准值、位置与关系、采集值／校正值、来源定位 | 可复核的观察或候选信息，不与已确认设计混写 |
| 房间信息与设计条件 | 所属楼层、用途、当前采用的尺寸／标高、门窗要求、需保留对象、装修／柜体条件等 | 当前设计所用条件；未知项明确留空 |
| 模型与图纸 | 已应用的建筑／室内／专业构件、视图、图纸及版本 | 继续使用原生工程存储和编辑权限 |
| 问题与决定 | 待量尺寸、冲突、解释、采用／放弃原因、变更及相关对象 | 支持持续设计，避免重复提问和丢失决定 |
| 派生资料与成果 | 识别文本、缩略图、检索摘要、索引，以及带输入版本的导出成果 | 前者可重建，后者可以独立交付；均不能替代原件 |

“来源类型”和“核实状态”分开记录。例如：用户提供、扫描测量、人工实测、公式计算、AI 推断是来源；待核实、已采用、冲突、已替代是状态。用户提供的尺寸也可能尚未现场复量，AI 生成的置信度不能冒充实际测量精度。

房间信息的常用内容：

- 归属与名称：楼栋、楼层、房间编号、用途、别名及相邻空间。
- 空间：轮廓、长度／角度、层高、完成面标高、吊顶／梁底高度、斜顶或局部异形；面积明确净量／毛量及扣除规则。
- 门窗洞口：所属墙、位置、宽高、窗台／门槛、开向及现场待核事项。
- 现场条件：柱梁、管井、可见设备／接口、照片与扫描参考；未观测或未知内容不补成确定事实。
- 设计条件：人数／用途、保留与不可改对象、家具／柜体需求、材料偏好、预算条件及安装间隙。
- 待办与来源：缺失项、尺寸冲突、已采用依据、最近修改和相关构件。

这些是按对象和任务显示的字段，不要求用户先填写一张庞大的表格才能开始设计。

## 三、资料与对象如何关联

所有资料和对象采用稳定身份。房间改名、文件移动或资料显示名改变，不改变关联；“厨房”可能出现在多个楼层，不能作为唯一标识。

| 记录 | 必要关联与版本信息 |
| --- | --- |
| 项目 | 项目身份、格式版本、当前工程版本、单位、坐标及入口目录 |
| 来源 | 来源身份／版本、内容摘要、原名、媒介类型、项目内相对位置、导入／采集信息 |
| 来源定位 | PDF 页码与区域、图片区域及方向／尺度变换、文本片段、扫描批次和采集对象；适用哪些就保存哪些 |
| 观察／条件 | 所属对象、属性、原始值与标准单位值、来源类型、核实状态、来源定位及替代关系 |
| 模型对应 | 原生构件身份与工程版本、采用的条件版本、来源／扫描对象对应 |
| 问题／决定 | 涉及的候选值、对象和来源、待答问题、已采用结论及操作记录 |

例如，手绘图写“厨房 3.6m”，另一条现场记录写“4.0m”，系统保留两条来源并显示冲突，当前已采用值有明确依据。若用户明确说“把厨房长度改为 4m”，按已授权编辑执行并记录替代关系，无需再为这一普通修改重复索要批准。

原图裁剪、透视校正或 OCR 修订后，定位仍能回到确定版本的原件；不能只保存一段脱离图片的识别文字。导入平面中的坐标与建筑坐标之间保留单位、比例、方向、原点和控制点关系。

量尺助手按相同方式入库：扫描批次是来源，实测与校正值是记录，墙／门窗／房间底稿是可编辑结果。照片、点云和网格是设备实际提供的参考类型；没有采集到的数据不生成假文件。多次扫描的坐标对应及人工校正属于可追溯记录。

## 四、用户怎样找到这些资料

建筑项目提供项目级“资料”入口；房间、楼层和构件详情也可打开相关资料，避免把资料混进所有专业的工具栏。

- 按“全部、待整理、手绘／图纸、现场照片、量尺记录、补充说明”等来源分类浏览。
- 按楼层、房间、构件、用途、时间、核实状态和版本筛选；支持名称、原文和别名搜索。
- 选择一个房间，查看“当前条件、相关资料、待解决问题、已采用决定”。
- 选择一个尺寸或构件，查看“依据来自哪里、采用了哪个版本”；从原图也能定位对应对象。
- 显示新旧资料、模型采用状态和仍未解决的问题；旧资料可追溯，不与当前依据混排。

“资料整理”和“改变建筑模型”是不同结果。AI 已归类不代表尺寸已经核实，识别出墙线也不代表完整建筑构件已经生成。

## 五、文件与存储组织建议

沿用现有 `.floeproject` 作品包与外层 `FloeProject.json`，以及 CAD 原件的现有存储。下列为拟议的逻辑布局，最终名称和迁移按原生存储实现确定：

```text
住宅.floeproject/
  FloeProject.json                 现有作品身份与入口元数据
  Document.floecad/                复用原生模型、构件、图纸及 CAD 版本存储
  Building/
    Records.sqlite                拟增：来源登记、房间信息、对应关系、问题和决定
    Sources/blobs/<摘要前缀>/<摘要>  原始字节按内容寻址；来源ID／不可变版本映射存在数据库
    Resources/<资源ID>/<版本>/     工程使用的补充资料与库资源，已由 CAD 保存的内容只引用
    Deliverables/<成果ID>/         独立成果、格式、范围和输入版本记录
    Derived/                      可重建的识别结果、缩略图、摘要与搜索索引
```

关键约束：

1. **一个事实有一个权威位置。** 模型几何和构件尺寸仍由原生模型负责；资料记录保存来源／设计条件以及对模型的引用，不另存一份可独立修改的同名模型。设计条件与当前模型不同应可见。
2. **一个来源版本只存一份原始内容。** 多个房间共享同一张户型图时保存多个关联；内容相同也保留必要的不同来源上下文。显示名可读，物理路径和身份分开。
3. **工程可完整带走。** 需要持久使用的资料进入工程管理，不只引用聊天临时目录或设备绝对路径。大资料可按需加载；打包／迁移明确校验依赖和未完成导入。
4. **索引可以重建。** 索引损坏不能让原件、尺寸和决定丢失。缓存的输入摘要、版本和识别配置与源匹配，更新仅使相关派生结果过期。
5. **助手会话不代替项目数据。** 项目补充记录与决定在项目中保存；重启／刷新助手不清空它们。会话归属和授权继续由现有服务保存，不从导入包里的文本或元数据获得权限，也不随工程导出携带授权。
6. **人和 AI 都有入口。** 界面可浏览与定位资料；AI 通过结构化读取获取目录、房间信息和来源片段。项目概览或摘要可导出为可读文档，但属于生成视图，不能变成另一套可随意分叉的事实存储。

项目级版本检查点需绑定原生模型版本与资料记录版本。跨文件变更采用可恢复的提交过程；失败时保留原始资料和旧的有效工程，不能只保存某一半后宣称全部成功。具体事务和恢复协议在实施包中验证。

## 六、AI 如何有效利用，避免每次重读全部文件

继续扩展现有项目工具的读取／编辑语义与权限链，不建立另一套依赖路径猜测的助手。

1. 解析并验证当前项目归属，读取小型项目概览：工程版本、楼层／房间目录、资料分类、待解决问题和近期变化。
2. 根据任务定位对象。例如“按厨房现场条件做橱柜”，先取厨房当前条件、柜体限制、水电接口记录及相关资料；不默认塞入整栋所有照片和专业报告。
3. 结构化筛选与全文检索结合，返回稳定资料身份、版本、来源片段及分页位置。语义检索是补充，不能成为已知房间／构件精确读取的唯一途径。
4. 需要视觉信息时，打开命中的原图／PDF 页或区域；遵守已有文档和 PDF 渲染服务。不能仅靠摘要完成含关键尺寸的视觉判断。
5. 把采用的条件版本与候选修改关联；执行前校验工程是否已变化，通过原生编辑会话更新并保存，保留撤销与失败恢复。
6. 更新受影响的房间资料、模型对应及结果状态。引用来源随输出保留；旧摘要、旧分析或旧导出不能冒充当前版本。

项目 AI 对资料中的内容按用户任务理解，但导入文档不能给自己授予工具权限。检索遵守当前项目及所选资料范围；跨项目使用必须是用户明确选择的输入。

整理可由后台任务持续完成，并显示“接收、识别、归类、待核对、已可用”等真实状态。取消、中断或重试保留已接收内容，避免同一资料重复入库；是否支持 OCR／视觉识别取决于实际配置和可用服务，失败仍可手动补充并定位原件。

## 八、实施时的代表性验收

| 操作 | 需要看到的结果 |
| --- | --- |
| 上传手绘、现场照片并补一段房间说明 | 原件完整，自动整理到明确对象；歧义进入待核对；每个采用值可定位来源 |
| 图片尺寸单位不清或图上值与现场值冲突 | 不默默取最新文件或放大置信度；显示候选依据，围绕当前任务提最少问题 |
| 用户明确纠正一个尺寸 | 一次普通编辑完成并可撤销，保留旧依据／替代记录，关联几何和结果相应更新 |
| 从量尺助手补扫相邻房间 | 扫描批次、坐标对齐、来源几何及当前设计分别可查，不覆盖已改模型 |
| 房间／项目改名、移动、重开或助手刷新 | 资料与对象对应仍有效；不依赖旧绝对路径或聊天附件存活 |
| 同一张图用于多个房间，或同一文件重试导入 | 内容不重复堆积，房间关联正确，导入可恢复并保留来源上下文 |
| 替换一页资料或修正识别文字 | 对应提取／索引更新，未受影响内容复用，旧版本仍可追溯 |
| 大量照片／扫描资料下查询单一房间 | 返回有界且相关的资料，支持分页和按需加载；性能以实际规模测量记录 |
| 保存中断或并发编辑 | 新旧工程版本不混用，可恢复到有效检查点，已接收原件不丢失 |
| 导出原生项目或独立二维／三维副本 | 各自依赖齐全，保留需要的来源说明；不导出助手授权，副本修改不回写原件 |

这些是待实施的验收目标，不是已经执行的测试结果。当前交付仍为方案文档；界面 Demo 尚未增加资料管理或量尺采集。

## 九、智能家居料单怎样进入项目

用户从智能家居工作台的“导入料单”或当前项目 AI 助手添加文件，均进入同一项目导入服务。建议支持 XLSX／CSV 表格，PDF／图片／拍照料单，文本文档及粘贴文字；原始格式、实际读取方式和识别结果分别记录。XLSX 读取单元格与显示值、公式及单位语义，CSV 检查编码／分隔符；PDF 优先读文本和表格，扫描件使用现有 OCR／视觉能力。不能因上传成功而直接显示料单入库完成。

导入流程：**接收原件 → 识别表格与列含义 → 规范字段／单位 → 匹配设备与资料 → 处理重复和缺失 → 形成项目料单与待办 → 关联点位、系统和图纸**。界面逐步显示真实进度；关键歧义可补充，其他已明确行继续整理。已授权的常规整理与入库不逐行增加许可对话。

| 内容 | 保存和处理方式 |
| --- | --- |
| 来源 | 文件版本及摘要、工作表／行／单元格或 PDF 页／图片区域、原始文字、导入批次 |
| 产品身份 | 品牌、系列、原型号与规范型号、订货号、变体及适用地区；别名作为检索条件，不冒充确定型号 |
| 设备与能力 | 类别、协议／网关要求、供电、安装形式、通道数与控制能力；资料未确认的保持未知 |
| 数量与包装 | 原数量、计量单位、包装换算、套件及附件关系、备用数量；台数、通道数、套数不能直接相加 |
| 工程归属 | 楼层、房间、系统、点位、回路／地址与安装高度；没有位置的数量保留待布置，不随意落到原点 |
| 业务状态 | 设计需要、报价、采购、到货及已安装分别记录；不同文件不无声覆盖其他用途的清单 |
| 匹配结果 | 固定到设备库资产版本及依据，或保留候选／未识别产品；能先作为自定义产品继续整理 |
| 价格信息 | 原币种、税与折扣／有效期等来源条件；无关方案设计的价格字段可不显示 |

同一物理设备可能有多个控制实体或通道，不能把实体数量当作采购数量。相同型号出现在不同房间时共享产品定义，保留各自房间和数量；多个厂家叫法相似时不自动合并。相同文件重试可复用来源和提取结果，不重复加数量；明确新版料单做差异对比，缺行是否删除／保留需按采用操作处理。

导入本身不凭型号创建已验证的三维模型、协议兼容性或孔位规则。库里没有该型号时，保留原行和资料，可由 AI 查找官方资料或整理用户补充文件，后续补全仍可追溯。点位已布置、待布置、备用、套件附件以及设备缺少电源／网关／控制接口等问题分别显示。

机器可读草案见[智能家居料单合同](design/building-project/smart-home-bom-v0.json)。这是新增领域设计，不改变当前 SQL／8 类表单或其 24 项历史检查范围。智能设备、物料行、点位和通道的正式表与原生对应仍需新增及验证，不能把这些数据塞进现有家具类型后视为完整支持。

## 十、给 AI 哪些整理文件的实际能力

AI 通过项目工具读取与执行，复用现有 `StudioCoordinator`、`StudioDocumentAccess`、文件服务和原生 CAD 会话。读取工具返回有界分页与出处，写入工具校验当前工程版本、任务归属和取消状态；资料中的文本不能授予工具权限。以下动作是拟议合同，当前未注册，不能提前出现在“已可用”工具目录中。

| 动作组 | 读取或修改内容 | 必须返回的结果 |
| --- | --- | --- |
| 资料目录／检索／读取 | 当前项目内已导入的文件、相关片段、页或区域、房间与对象筛选 | 稳定来源 ID／版本、分页／定位、读取范围与真实缺失状态 |
| 资料提取 | 对选定来源调用已有表格、文档、OCR／视觉读取能力 | 原始值／单位、候选字段、出处、识别问题及实际所用服务 |
| 资料整理 | 调整显示名、分类、标签、关联房间／系统／设备，拆分成逻辑条目、建立去重关系 | 变更前后、原件身份、受影响关联、撤销／修订与保存回执 |
| 料单预览与采用 | 字段映射、型号候选、数量与单位、差异、选定采用范围 | 已采用行、未解决项、设备／点位关联、工程修订及真实保存状态 |
| 条件整理与模型编辑 | 将有依据的条件写入资料记录，再通过原生动作修改已授权对象 | 条件采用依据与模型变更分别记录，关联图纸及清单状态可查 |

首选扩展现有 `studio.read`／`studio.edit` 与建筑动作分派的项目语义；最终动作名由对应实现确定，不另开绕过服务的任意路径／SQL／宿主脚本入口。当前建筑动作源码仅有目录、读取、添加直墙和矩形房间，尚不具备上述完整资料能力。本轮只核对源码与设计工具合同，没有修改运行时工具目录。

整理可改变项目中的可读名称、分类与关联，同时保留原文件名和原始内容。物理归档由存储服务维护，AI 只使用稳定资料身份；重新命名或移动不让链接失效。新 OCR、裁剪、拆页或解析结果成为派生资料／新版本，不覆写唯一原件。删除与外发继续沿用已有权限规则。

例：“把这批料单和说明书按房间、系统整理，补进智能家居方案。”助手应读取本项目资料，提取清单与说明书，按准确型号和房间建立关系，直接完成明确的已授权整理；将无法确定的型号／数量／归属集中为少量待答问题。完成后能从料单行打开原 Excel 单元格或 PDF 页面，也能从设备点位找到对应说明书。刷新助手、工程重开、改房间名后这些关系继续存在。

新增验收目标：重复导入不翻倍；新版料单可比较；数字／单位识别错误不成为静默确定值；套餐不被错误当作单台设备；已购不覆盖设计需求；文件改名不丢出处；取消／中断保留原件及已完成整理；AI 越界读取被拒绝；错误保存不产生假完成状态。上述行为仍待实际实现与验证。
