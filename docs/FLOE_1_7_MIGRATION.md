# Floe 1.7 迁移与恢复 / Migration and recovery

1.7 尚未完成迁移验收。本页区分已有机制与上线前必须完成的步骤，不应据此直接迁移唯一一份用户数据。详见[实施状态](FLOE_1_7_IMPLEMENTATION_STATUS.md)。

## 数据与环境语义

环境查找顺序为 `session > project > shared > base`，写入目标显式指定。会话环境属于对应对话和项目；不能以第一个项目或默认临时目录代替真实归属。这是依赖、数据和生命周期分层，不是同进程原生代码的安全沙箱。

数据库 v40 为后台任务加入 `environment_id`；旧任务字段可为空，迁移成功不等于所有旧任务都已正确绑定运行环境。环境登记使用版本化数据与匹配的日期解码，损坏登记不能悄悄当作空环境。基础版本改变应标记需要重建，保留用户层数据。

## 当前恢复机制

- 删除环境先停止所属任务与执行器，停止失败保留登记及引用；不能提前释放 CAS 或关闭其他环境的会话。
- 软件包变更采用 `.floe-package-transaction` 文件日志。未完成事务在下一次包变更前恢复；已提交标记与备份用于区分提交和回滚。恢复失败保留现场，不把损坏状态当成功。
- 升级/卸载检查文件归属及已记录的摘要；本地修改需要处理冲突，不能静默覆盖。当前维护脚本与不支持的文件类型明确拒绝。
- 媒体导出先写临时输出，验证后提交。失败或取消应保留原文件；不能依据成功文案删除源素材。

## 迁移上线前仍须完成

旧工作区首次打开时建立对应项目环境，复制/迁移依赖前保存可恢复副本；验证原工作区、会话归属与依赖搜索路径。模板、晋升、配额和共享 CAS 的引用变化必须覆盖重启与中断测试。旧依赖恢复入口及基础层重建流程仍需完整连接。

数据库升级后，不要直接用旧 App 打开新数据库或手动降低 schema。回退应使用升级前一致的数据库和依赖备份，并验证对应旧版本能读取。具体自动迁移/恢复 UI 未验收前，不把它描述为可用按钮。

## 故障取证

保留当前版本/提交、所属环境、失败阶段、脱敏错误、事务日志及恢复副本的位置。不要手动删除 CAS、登记文件或事务目录来掩盖失败。先确认执行器实际停止，再通过受支持的恢复路径重试；恢复完成后重开工作区并验证依赖和文件内容。
