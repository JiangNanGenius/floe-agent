## 第二轮预研发：完整工程链路

用户判断“距离模块闭环还早”与当前证据一致。已有 UI、资料库和计算组件是基础，尚不能完成一套装修工程。新建的 [12 条验收场景](../design/building-project/closure-scenarios-v2.json)采用同一套合成装修工程、稳定房间／墙／门身份、冲突量尺来源和固定版本真实家具元数据，覆盖全部 28 项 QA。场景文件只是后续可执行验收的输入与预期，状态仍为 `NOT_CLOSED`。

独立源码调查形成 [原生能力与缺口清单](../design/building-project/native-core-gap-v2.json)：25 项能力、26 个复用接口和 8 个实现包。路径、符号、引用行及证据索引已记录；这是一份源码调查，没有因此增加任何运行通过项。协调者复核后的主要结论：

### 成熟产品工作流对本轮设计的影响

- 家具摆放需要把二维、三维、家具列表、楼层和真实尺寸放在同一工程中处理；参照 [Sweet Home 3D 官方指南](https://www.sweethome3d.com/users-guide/)。本轮借鉴交互与数据流程，不把其整套编辑器或 GPL 代码嵌入自有核心。
- 板件尺寸需要明确局部轴、材料类型、封边扣减策略、实际原板／余料和木纹；参照 OpenCutList 的[材料](https://docs.opencutlist.org/features/applying-materials)、[构件轴](https://docs.opencutlist.org/getting-started/components)和[裁切图](https://docs.opencutlist.org/features/parts/parts-list/cutting-diagrams)文档。排板输入齐全不等于已找到可行排板，更不等于完成五金加工。
- 品牌配置器连接柜体、五金选择、清单和制造资料；[Blum Cabinet Configurator](https://www.blum.com/ca/en/services/planning-construction-product-selection/cabinet-configurator/)是工作流参考。其 [FAQ](https://www.blum.com/ca/en/services/faq/)说明 BXF 为专有接口；公开下载或文件可见，不代表已有可嵌入的公开接口或合作授权。实际接入仍走官方数据、合作包和用户导入。
- 视觉材质与建筑材料层／工程属性应分别记录；参照 [Bonsai 的几何与材料模型](https://docs.bonsaibim.org/studio/reference/geometry_and_materials/index.html)。贴上木纹不能自动得出防火等级、热工参数或无线衰减。
- 多房间扫描要保留采集坐标关系，并经过房间／结构合成；[Apple RoomPlan 多房间流程](https://developer.apple.com/documentation/roomplan/scanning-the-rooms-of-a-single-structure)提供系统接线参考。当前没有运行该设备流程，普通摄像头的引导量取与实测校准仍是独立实现。

### 本轮新增源码

`FurniturePlacementPlanner` 已编写明确源单位／目录尺寸拟合、正交源朝向、底部或几何中心锚点、楼层标高、安装高度及旋转，输出 CAD 原生矩阵；资产版本、原文件和依赖哈希参与失效判断。对真实固定版本扶手椅的核查发现：原始 OBJ 包围盒乘以 10 不等于目录声明的 594 × 627 × 1050 mm。因此拟合目录尺寸与“已知源单位为厘米”必须分开，不能假报源单位。10 项测试已编写，尚未实编译／运行；这是纯值适配器，没有执行家具导入、真实碰撞或渲染。

`CabinetManufacturingPlanner` 已编写每板显式工艺：局部长度／宽度轴、设计是否含封边、规则来源与版本、四边封边、轴向总加工余量、木纹及允许转向。分别输出设计面、完成、基材与开料尺寸；实际原板和余料保留规格、材料版本／厚度、数量、修边和木纹。缺条件保留缺项，不猜 2440 × 1220 原板、锯缝或孔位。生成的是带逐库存转向约束的排板输入，不是优化结果；`readyForNesting` 只表示输入条件齐备，`manufacturingVerified=false`。14 项测试已编写，尚未实编译／运行。

两组新增 24 项测试不在旧 123 项通过证据中。下一次定向 Core 验证应运行旧 Core18＋新增24，共42项；即使全部通过，也只增加24项新的独立用例覆盖，不应把重跑的18项重复计数。独立 Core-only runner、单独源码快照和构建目录已就绪，等待新的共享原生窗口；不使用已结束的 UI03 窗口或修改其冻结快照。

### 项目数据所有权与保存恢复合同

以下为需要实现并用失败注入验证的合同，尚未成为现有能力。源码调查的 journal 建议不能直接等同于跨库事务。

| 数据 | 权威位置与关系 |
| --- | --- |
| 原生墙、房间边界、家具实例、柜体板件和图纸 | 同一 CAD 文档；Records 用稳定锚点引用，不另存一份可独立编辑的几何真相 |
| 原件、定位、观察、采用决定、资料与料单版本 | Records；保留原始值与历史；采用到模型是明确的项目修改，不靠双向静默覆盖 |
| 家具／材质／五金文件 | 不可变资源版本及完整依赖；工程引用固定版本；目录更新不改旧工程 |
| 图纸人工内容 | 现有图纸模型持久化；自动几何和尺寸依赖稳定构件／实例／板件锚点，失联时保留并提示 |
| 长任务与结果 | 项目服务拥有生命周期；结果绑定完整输入版本，视图切换不重启，修改后标过期 |

拟采用“不可变工程代次＋最后发布 manifest”的原型，而不是依次覆盖 CAD 和数据库，再假定回滚旧文件即可：

1. 捕获项目身份、当前 manifest 代次、CAD revision／内容摘要及 Records 各组件基线；保存期间新增编辑留在后续草稿。
2. journal 记录提交 ID、预期基线、拟发布代次和每段摘要。CAD 快照写入新代次；Records 追加待发布版本。现有 Records 还没有工程代次可见性过滤，必须新增并迁移，不能把当前各自 CAS 当作已具备该合同。
3. 对新代次读回，核对项目身份、CAD／资料版本、资源固定引用与图纸输入。两段任一失败，当前发布代次仍指向旧成果；来源文件和失败输入保留。
4. 在项目协调锁下再次比较预期代次与所有基线，再用有条件的原子发布切换 manifest。此发布点决定对外可见版本；只靠普通文件替换而没有基线比较，不满足 CAS。跨进程、外部 CAD 编辑与多窗口冲突必须实际验证。
5. 发布后补记 journal／数据库完成状态。崩溃恢复首先查看 manifest：已指向本提交则补记；仍指向基线则恢复或放弃本提交；已由其他提交推进则进入冲突恢复，绝不拿旧 `previous` 覆盖更新成果。

最低失败注入包含：准备后退出、CAD 快照完成后退出、Records 追加后退出、manifest 切换后退出、写满／写入错误、缺资源、CAD 外部修改、多窗口竞争，以及保存中继续编辑。每次都须证明重开只显示一个一致代次，或者明确进入可恢复状态；不能只检查“有一个 journal 文件”。

### 继续开发的边界

八个实现包按技术依赖推进，全部功能范围继续保留，不要求用户删减或再次排功能优先级。先把项目身份、保存恢复和原生锚点接通，再接家具准入、柜体原地更新／正式组合图、独立导出，以及资料／AI／专业工作台的同工程联动。每包须交付可打开的工程、实际结果和失败恢复证据；源码、对象编译、组件测试、iPad 操作和完整工程验收分别记账。
