# Office 前端逐项实施与验收

本文件是 [本轮升级总计划](WORKFLOW_UPGRADE_IMPLEMENTATION.md) 的 O01–O05、F04 明细，不缩减其他升级目标。2026-09-09 用户再次确认：**接入完整编辑器界面不等于完成编辑功能；不能只验证文字和单元格便宣称完整 Office。**

当前结论：Office 前端仍在实施，未完成。下表中的“局部验证”只对应明确记录的样本操作。现有上游菜单、UNO 命令或导出 API 的存在，均不能代替用户实际操作成功。

## 统一操作与证据规则

- 右侧检查器只读，进入全屏后才允许编辑；新增按钮和快捷键也必须遵守这个边界。
- 采用正常文档页面、表格网格和幻灯片画布，保留选区、光标和对象操作；禁止退化为逐字段表单。
- 每项分别记录：入口可达 → 用户完成操作 → 撤销/重做 → 原格式保存 → 关闭重开 → 内容/位置/样式对照。缺少任一相关环节，不能标为完整通过。
- 数据检查和视觉检查分开：值正确不等于格式正确，坐标存在不等于画面正确，附件关系存在不等于附件字节完整。
- 独立 Mac Designed for iPad 测试、完整 Floe 文件会话、物理 iPhone/iPad、Microsoft Office 重开分别记录。不能相互替代。
- 每个故障保留输入样本、步骤、截图、保存产物摘要、实际失败项；未修改对象也要验证是否被意外改动。

附件指真正随 DOCX/XLSX/PPTX 保存的文件或嵌入对象。普通超链接、文件名文本、截图、旁边保存的原文件，均不能代替附件嵌入。将 PDF 页面转成图片插入，与把 PDF 原文件作为附件插入，是两个不同操作。

## 已核实的通用附件断点与实现顺序

1. `browser/src/control/Control.NotebookbarWriter.js` 等菜单具备图表/图片等上游入口，不构成通用附件实现。
2. `browser/src/map/handler/Map.FileInserter.js` 的移动文件导入通过 Base64 `insertfile` 消息处理现有类型；需要独立附件传输契约、错误回执与会话文件生命周期，避免将大附件作为模型文本重新生成。
3. `kit/ChildSession.cpp` 的 `insertFile` 类型列表和 `postInsertCommand` 目前覆盖图片、背景、比较和音视频；移动分支断言仅 graphic/multimedia。没有通用 attachment/object 类型。必须补齐处理，不能复用图片分支而错误报告成功。
4. `ios/Mobile/DocumentViewController.mm` 的 `UIDocumentPickerDelegate` 目前处理导出临时文件清理，没有通用附件导入回调。需要区分导入/导出任务、取消和错误、授权读取与会话副本。
5. `engine/sw/source/uibase/shells/textsh.cxx` 中 `.uno:InsertObject` 的处理读取对象类 ID，而不读取文件 URL；不能只传 `FileName` 便声称插入附件。`SwWrtShell::InsertObject` 已有嵌入对象/图标逻辑，应复用正确的对象创建路径并验证移动构建能力。
6. 先打通 Word 一个真实嵌入附件闭环，再落实 Excel/PPT 对象锚点与各自保存格式；继续验证新增附件、修改附件及“未修改附件保留”三类场景。此顺序不免除上表任何其他功能。

优先修复实际缺失入口和传输/嵌入/保存链路，再按上述矩阵完整实测。最终发布说明、模型工具和 Skill 介绍必须与逐项结果一致；不能用功能列表或上游宣称替代验收。
