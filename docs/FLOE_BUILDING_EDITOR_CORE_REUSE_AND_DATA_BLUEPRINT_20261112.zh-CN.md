日期：2026-11-12。状态：源码／官方资料调查、数据原型及独立柜体组件验证；不是完整 App 实现或专业计算验收。本轮读取基线为 `59c57650ea80fc95ae809de5a2241187229c86c4` 的当前工作树，保留其他任务的未提交修改。后续真实实体、出图及视觉缺陷证据见[组件预研记录](qualification/FLOE_INTERIOR_COMPONENT_20261112.zh-CN.md)。

## 一、固定边界与推荐组合

用户明确要求继续使用 Floe 自己的二维、三维编辑核心，寻找成熟项目解决中间的建筑语义、几何转换、交换和家具资源问题。该要求优先于任何替换整个编辑器的建议。[28 项已确认 QA](FLOE_BUILDING_EDITOR_REQUIREMENTS_QA_20261112.zh-CN.md)继续有效，用户又直接追加内部表单／小数据库、成熟内核复用、家具库来源、用户导入与 AI 创建家具。

最新产品优先级是以室内装修作为默认工作流，重点补齐柜体结构与成套室内施工图；完整建筑／结构／机电范围仍保留。具体目录和已有出图能力／规模缺口见[室内施工图与柜体深化](FLOE_INTERIOR_DRAWINGS_AND_CABINET_DETAILING_20261112.zh-CN.md)。

建议采用：**原有 Floe CAD + 现有 OCCT／几何库 + 建筑领域与转换服务 + 项目 SQLite／GRDB + 版本化资产库**。中间服务输出 Floe 原生构件、几何和图纸对象；外部项目的界面、渲染器、项目权限和撤销栈不替换 Floe 的对应部分。

```mermaid
flowchart LR
  I[手绘、说明、扫描、导入模型] --> N[识别、单位与坐标规范化]
  N --> D[项目资料库与内部表单]
  D --> B[建筑、室内与柜体领域服务]
  B <--> C[Floe 二维和三维核心]
  B <--> X[IFC与资产格式适配]
  C --> S[平立剖、图纸和独立副本]
  L[版本化家具与材质库] --> B
```

领域数据、模型和资料有明确分工：原生模型保存几何及构件事实，资料库保存依据、设计条件、对应关系和决定；可重建的检索索引有输入版本，不产生第二套可独立修改的模型。

## 二、“转换内核”拆成六条可验证的链

| 转换 | 输入／结果 | 需要保留的关系和限制 |
| --- | --- | --- |
| 平面 CAD → 建筑 | 带单位、图层和对象身份的线／弧等 → 墙、门窗、空间候选 → 原生建筑构件 | 区分中心线、墙边线和标注；缺少层高或墙厚时保留待补状态；明确处理弧线、T／十字交接、开口宿主 |
| 手绘／零散说明 → 建筑 | 图像与文字 → 来源定位和结构化条件 → 可编辑底稿 | 视觉识别与确定性几何处理分开；错误识别不覆盖已确认条件；保留尺度、旋转和候选歧义 |
| 建筑构件 ↔ 原生几何 | 墙轴线／构造、门窗宿主、楼板轮廓、柜体装配等 ↔ Floe 特征与体／面 | 对象身份、类型／实例、来源和重建后面身份；二维编辑改变同一语义对象，不维护彼此分叉的平面和三维副本 |
| 三维 → 平立剖／图纸 | 版本化体、切面和投影条件 → 可编辑线、剖切、填充及关联图纸 | 复用几何剖切与隐藏线；尺寸、标签、详图和图签独立保存且有模型对应 |
| 原生模型 ↔ 通用格式 | IFC／STEP／DWG／DXF／GLB等 → 明确表示类型的原生对象或独立文件 | 单位、坐标、类型、实例、层级和资源依赖；不能将三角网格标成参数实体或承诺恢复完整建模历史 |
| 扫描 → 建筑底稿 | RoomPlan／引导量尺及实测校正 → 有坐标对应的多房间底稿 | 公共墙、门洞对齐、原始与校正值、补扫和遗漏；不从外观推断未知构造、承重或隐藏机电 |

统一适配合同至少包含：输入来源和版本、单位、坐标系与变换、类型化对象、原生／外部身份对应、资源清单、不支持／丢失信息、算法版本、误差／近似规则和预期工程版本。错误与取消产生可恢复结果，成功需经过真实导入／导出读回。

后续已沿 OpenCutList 源码找到其实际 C++ 排板依赖：固定 MIT PackingSolver fork，可作为独立原生算法候选；OpenCutList／Packy 本体仍分别有宿主、许可与共享库封装边界。具体构建依赖、尚未运行的范围及制造数据合同见[柜体制造与排板预研](FLOE_INTERIOR_MANUFACTURING_REUSE_20261112.zh-CN.md)。

特别发现：IfcOpenShell 当前 `v0.9.0` 快照的 CMake 在非 WASM 下拒绝 `BUILD_SHARED_LIBS=OFF`；`0.8.0` 分支快照仍提供静态配置。所以下一步应在固定来源上验证原生库封装和现有 OCCT 兼容性，不能直接宣称“下载最新版即可静态塞入 App”。[0.9 构建源码](https://github.com/IfcOpenShell/IfcOpenShell/blob/b0ab9ec2f50699854911c9621182929a525bb420/cmake/CMakeLists.txt)、[0.8 构建源码](https://github.com/IfcOpenShell/IfcOpenShell/blob/481676e51b65cb93e520b9f073123f22a06b212b/cmake/CMakeLists.txt)。这两个快照是调查输入，还不是批准的分发依赖。

OpenPlan3D 处理 RoomPlan 米制、Y-up、列主序矩阵到平面厘米；Floe 应通过单一适配边界转换到自身单位／坐标，并保留第三维和来源变换。[导入源码](https://github.com/laanlabs/openPlan3D/blob/b0727b54da5f0f642722dcc88cc52d7236fadc9e/src/lib/utils/roomplanImport.ts)。其[房间识别](https://github.com/laanlabs/openPlan3D/blob/b0727b54da5f0f642722dcc88cc52d7236fadc9e/src/lib/utils/roomDetection.ts)和[墙面洞口](https://github.com/laanlabs/openPlan3D/blob/b0727b54da5f0f642722dcc88cc52d7236fadc9e/src/lib/utils/wallProfiles.ts)可做具体移植对象。后续已实际执行固定墙面源码的 10 个检查，未运行完整项目、房间识别或 RoomPlan 导入，也未完成 Swift 移植。

## 四、内部表单与小数据库的具体设计

采用项目内 SQLite，通过现有 GRDB 访问。固定的项目、对象、来源、版本、资产、实例、决定和操作记录采用明确表；可扩展属性通过统一字段定义限制数据类型、单位和范围。UI 表单和 AI 使用同一字段及同一项目服务。

已制作[SQL 原型](design/building-project/schema-v0.sql)、[8 类表单定义](design/building-project/forms-v0.json)和[验证脚本](design/building-project/check_design.py)。覆盖：房间档案、资料登记、尺寸核对、家具定义／实例、柜体设计与生产准备、资源入库、AI 创建家具、待补与冲突。

| 内部数据 | 保存规则 |
| --- | --- |
| 对象和原生对应 | 稳定身份及楼层／房间归属；体／面与构件对应到原生工程，不在 SQLite 再存可独立修改的几何 |
| 原始资料 | 内容摘要和相对路径登记，同一原件可关联多个对象；按版本保留原文、图片定位及扫描信息 |
| 提取／实测值 | 原始来源与标准单位值对应，类型与范围校验；不清楚的单位先留待核对，不能猜成合法数值 |
| 当前采用值 | 指向具体观察与决定，旧值、冲突和替代链保留；录入新观察不自动覆盖当前依据 |
| 资产与实例 | 定义、版本、依赖、入库完成状态和放置实例分开；新库版本不改变旧实例 |
| 检索 | 按对象与属性精确读取，再读相关来源；FTS 索引可重建，并带输入指纹 |
| 操作历史 | 复用服务任务的身份、引擎版本、幂等键、输入摘要和预期工程版本；不在项目库再造调度器 |

表单中的“设计长度／净高”等资料条件与模型实际值分别可见。模型尺寸修改走 Floe 原生编辑动作；表格编辑不旁路特征重建、撤销和保存。未知自定义字段按类型扩展，不把承重、开洞或制造规则塞进任意文本后直接执行。

完整保存还需项目协调器绑定资料版本、CAD 版本及依赖清单；跨数据库／CAD 文件不是一个 SQL 事务就能解决。实施时需准备记录、预期版本校验、可恢复提交及撤销对应，读回验证完成后才显示整工程保存成功。当前原型仅验证数据库一侧，未声称跨存储已原子化。

中文搜索需要原生分词／词条与结构化筛选配合；默认 `unicode61` 不等于完整中文分词。原型测试使用明确的中文词条。索引为派生内容；备份使用 SQLite Backup API 或已验证的等价快照方法，不直接复制正在写入的主库文件。[FTS5 官方文档](https://www.sqlite.org/fts5.html)、[Backup API](https://www.sqlite.org/backup.html)。

## 五、家具和材质从哪里来

初期来源采用可控的组合：

1. **Sweet Home 3D 的独立模型包。** 官方有按许可区分的 OBJ／MTL／贴图和 SH3F 库，优先核验其 BlendSwap CC0 子集；其他包分别保存 Free Art／CC-BY 署名要求。程序代码许可和模型许可分开处理。[官方资源包](https://www.sweethome3d.com/import-models/)、[模型与许可](https://www.sweethome3d.com/free-3d-models/)。
2. **Poly Haven。** 提供 CC0 模型、PBR 和 HDRI，选用适合建筑展示的具体条目。调用在线 API 时遵守单独的标识及来源展示要求；资产许可不等于其 API 服务代码许可。[资产许可](https://polyhaven.com/license)、[API 条款](https://github.com/Poly-Haven/Public-API/blob/master/ToS.md)。
3. **Kenney Furniture Kit。** 可作为低复杂度布置资产候选，官方搜索资料标明 CC0；本轮页面抓取受限，尚未核验下载包及具体条目，不把它标成已入库资源。[官方入口](https://kenney.nl/assets/furniture-kit)。
4. **ambientCG。** 作为材质／PBR 候选来源，沿用此前已查阅的 CC0 许可和逐项资产来源登记。[许可](https://docs.ambientcg.com/license/)。
5. **用户导入与厂商资产。** 接收当前格式服务实际支持的文件与资源包，保留其来源与使用条件；不能把“网上可下载”当成整库重分发许可。

具体来源与尚未验证的条目见[资源目录方案](design/building-project/asset-sources-v0.json)。后续取得一个固定 CC0 素材包，175 条目录完成离线基础检查和数据库暂存，其中 6 条资源待修复，尚未进入 App 原生素材库，详见[真实家具目录](FLOE_INTERIOR_FURNITURE_INTAKE_20261112.zh-CN.md)。现有 Demo 的简化家具仍是界面示例，不能用来代替这些真实素材的导入验证。

库定义、项目采用版本、放置实例三层分开。库可供多个项目浏览；工程保存所用的确定版本及必要依赖，实例保存位置、标高、朝向、参数与局部材质。可共享渲染资源以控制多实例开销，是否使用硬件实例化以原生核心实际能力验证。

## 六、用户导入和 AI 创建家具

导入流程：**选文件／库包 → 解析与依赖核验 → 单位、朝向、锚点和尺寸 → 材质槽及二维符号 → 入库版本 → 放置实例**。优先利用已有 GLB／glTF、OBJ＋MTL／贴图、USDZ、STEP 等实际服务；SH3F 需要专门包解析适配，FBX／DAE／3DS 等按 Assimp 或既有转换器逐项确认，不先承诺全部可编辑。

AI 创建分两条明确的路线：

- **参数化家具／柜体。** 用描述、尺寸、参考图和项目条件形成受约束的定义，通过已有原生特征／ShapeScript 等机制创建桌、柜、板件或装配；参数与结构可继续编辑。生成的配方、输入资料、引擎版本和失败记录保存在项目／资产版本中。
- **自由造型网格。** 对异形椅、软包沙发等采用可配置的模型生成后端，完成后按普通模型入库流程核验尺度、资源和材质。它可用于摆放和外观编辑；不能自动拥有板件、五金、孔位或完整建模历史。

TripoSR 是图像转网格候选，官方说明代码与预训练模型为 MIT、默认推理示例约需 6GB 显存；本轮只读来源，没有运行或移植到 iPad。文本生成家具仍可先走原生参数化路线；该候选不代表已解决文本到任意可制造家具。[官方源码与范围](https://github.com/VAST-AI-Research/TripoSR)。模型／服务使用沿用用户已有配置、授权及任务生命周期，不把开发者持有订阅作为功能前提，也不增加平行的代码执行或权限系统。

两条路线均提供候选比较、局部修改、取消、保存为库版本与放置；使用已有实例作参照时不直接覆盖它。材质、模型文件和生成输入也纳入同一来源链。

OpenKitchen3D 的官方资料适合参考产品定义、柜体沿墙组合、填板／台面和多视图派生，但它明确说明尚无切割清单／CNC，公开链接的引擎仍指向 OpenPlan3D。不能将该网站的 MIT 声明当成全部生产内核已经可下载的证据。[项目模型](https://openkitchen3d.com/docs)、[当前制造边界](https://openkitchen3d.com/faq)。QA 16 的完整生产准备仍需板件、封边、连接、五金孔位、纹理、锯缝和机床规则的独立实现与验证。

成熟复用路径已经追到：

- **Home Assistant**：参考房间、设备、实体／通道、网关及集成模型；其 API 可以作为用户明确选择后的系统适配候选。一个物理设备与多个控制实体分开保存，可避免把实体数当设备采购数。官方 REST／WebSocket 与注册表文档是可用依据，但不意味着我们已经连接某一实际家庭，也不意味着自动支持所有协议。[设备注册表](https://contributors.home-assistant.io/core/integrations/device-registry/)、[房间注册表](https://contributors.home-assistant.io/core/integrations/area-registry/)、[REST](https://contributors.home-assistant.io/core/internals/rest-api/)、[WebSocket](https://contributors.home-assistant.io/core/internals/websocket-api/)。
- **OpenStudio／EnergyPlus**：研究其建筑分析模型、负荷／设备系统及计算流程的适配，Floe 保留自己的编辑核心。官方 OpenStudio SDK／CLI 面向 Windows、Mac、Linux；没有据此认定可直接原生链接 iOS。若采用计算服务，沿用现有环境、任务和可恢复结果链，保存输入与引擎版本。[OpenStudio 官方](https://openstudio.net/)、[SDK 源码](https://github.com/NatLabRockies/OpenStudio)、[EnergyPlus 源码](https://github.com/NatLabRockies/EnergyPlus)。

## 十、图例、端口与线路需要同一份语义

用户明确追加 RS-485、CAN、“带零线的插头”、低压供电等预设。图例要区分**平面安装符号、系统拓扑符号、实际端子／接线表达和二维／三维设备外形**，分别关联同一设备实例和库版本。线条颜色、线型与缩放由图纸模板控制，连接关系由端口／节点决定；线条交叉不能隐式变成电气连接。

| 预设组 | 需要记录的工程含义 |
| --- | --- |
| RS-485 与串行总线 | 设备实际端子名、信号对、收发方式、参考与屏蔽、网段／地址及终端配置；上层协议另存，不因写着 RS-485 就默认是 Modbus |
| CAN | 按实际 CAN 类型和设备资料记录端子、网段、速率、终端及隔离／参考条件；相同线名不自动证明上层协议兼容 |
| 交流与接插件 | 插头／插座／接线端子形式、额定条件、L／N／PE、回路和设备零线要求；不把“需要零线的开关”与插座种类合成一个含糊符号 |
| 低压供电 | AC／DC、实际电压／极性、额定与需求功率、电源归属、线路与保护／压降计算依据；示例电压不成为所有设备的默认值 |
| 控制与照明 | 干接点 COM／NO／NC、继电器通道、调光或数字控制端口、传感器／温控器；信号参考不等于保护接地 |
| 网络与无线 | 网口、PoE 电源／受电关系、交换机、AP、网关、天线／无线连接；逻辑网络、实体线缆和供电关系分别登记 |

连接检查应能发现端口种类不符、供电条件不匹配、缺电源／网关、通道或端口不足、连接未完成等，并保留实际依据。终端、屏蔽、隔离及拓扑规则按具体设备、线缆和接口条件验证，不把常见经验硬写为普适规则。TI 的接口资料明确讨论这些条件，作为规则来源候选而不是本项目已完成的总线验收。[RS-485 官方应用资料](https://www.ti.com/lit/an/slla272d/slla272d.pdf)、[CAN 官方应用资料](https://www.ti.com/lit/an/slla486c/slla486c.pdf)。

当前 EDA 模块已有 KiCad 符号／引脚适配和远程元件库，可研究复用对应数据解析及资源服务；建筑点位与施工符号仍需自身领域模板，不能直接拿芯片引脚图替代。KiCad 库采用 CC-BY-SA 4.0 及设计输出例外；重新分发库集合仍保留其许可／署名，程序源码许可另计。[现有 EDA 库记录](FLOE_ELECTRONICS_LIBRARY.md)、[KiCad 库许可](https://www.kicad.org/libraries/license/)。本轮未修改 EDA 源码或把这些预设装入 App。

## 十一、AP 布置与无线信号估算

AP 布置使用同一房间和三维安装坐标，关联型号、频段、天线方向／增益、安装高度、发射条件、信道／带宽和网络／PoE 需求。按项目与设备实际适用条件设置参数；不能仅由“支持 Wi-Fi”推定全部频段或覆盖能力。

估算输入保存墙体／楼板厚度和无线材料参数、门窗／开口、AP 及接收面坐标／方向、频率、设备参数、其他 AP／干扰假设和算法配置。渲染材质的颜色或贴图不能代替无线衰减／介电参数，未知项及假设在结果中可查。

结果设计包括分楼层／分频段覆盖热力图、接收功率、覆盖空缺、覆盖重叠及信道协调建议；SINR／容量／漫游等只有在相应输入与模型具备时输出。估算、射线计算和现场测量保留各自状态，可用实测点校正模型并保存校正依据，不把模拟值冒充终端实测 RSSI，也不从一张功率图直接承诺实际吞吐。

QA 27 已确认快速估算、精细传播仿真和现场校准全部提供，计算精度可选择，精细计算是有进度、可取消和可恢复的独立任务。输入快照绑定房间／材料／AP 参数，结果保存计算范围、网格、配置和实际完成状态。现场测量保留设备／频段／位置及测量条件，校准产生新的模型参数版本，不覆盖原始测量，也不包含对 AP 配置的下发。

**Sionna RT** 是进一步研究的成熟无线传播候选：官方提供传播路径和接收功率／SINR 地图，CPU 路径需要 LLVM／Dr.Jit，依赖和资源预算需实际验证。它是可选计算后端候选，不能据文档宣称已在 iPad 上实时运行。[无线地图官方示例](https://nvlabs.github.io/sionna/rt/tutorials/Introduction.html)、[安装与 CPU 条件](https://nvlabs.github.io/sionna/installation.html)。本轮没有安装或运行 Sionna。

## 十二、三维灯光模拟与工程照明结果

QA 28 已确认三维灯光模拟两类结果都要：可交互三维灯光效果，以及基于真实灯具配光的照度分布、统计和报告。方案区分但关联三维效果中的灯光／光色／阴影／曝光，与基于灯具光度资料和明确计算条件的工程结果；效果画面不能单独证明照度达标。

同一灯具实例保存型号、安装位置／朝向、光源／配光版本、调光状态、回路和控制分组；实际取得 IES／LDT 等文件时按真实格式及转换能力记录。缺少型号光度文件时可供外观方案调整，但对应工程结果标明缺失依据。材质外观和计算所需的反射／透射参数分别保存，不能只取贴图亮度代替材料测量数据。

工程计算输入包括房间几何和遮挡、灯具光度与输出状态、材料参数、计算网格／工作面高度、室外／自然光和时间条件（若计算）、维护等方法所需参数。输出关联输入版本、引擎与配置、计算面、照度分布和报告；地区指标与未检查项沿用 QA 12 的规则来源／覆盖记录。模型、灯具或材料变更后结果标记需更新。

**Radiance** 可作为光度计算参照／后端候选，官方 `ies2rad` 将 IES 灯具数据转换成场景表达。格式坐标、灯具朝向和光源形状近似均需适配验证；它不证明 LDT 已有可用转换器或所有灯具都能无损恢复。[官方转换器说明](https://www.radiance-online.org/learning/documentation/manual-pages/pdfs/ies2rad.pdf)。本轮仅调查资料，未运行照明计算、设备性能或原生集成。

工作台和仿真数据草案见[系统合同](design/building-project/building-systems-workbenches-v0.json)，料单与 AI 整理见[项目资料方案](FLOE_BUILDING_EDITOR_PROJECT_INFORMATION_DESIGN_20261112.zh-CN.md)。这些追加设计没有改变此前数据库／柜体切片的验证范围，也没有并入当前稳定版发布。
