# 家具库：真实素材包、依赖检查与可检索目录原型

日期：2026-11-12。状态：完成离线文件检查、SQLite 暂存／检索原型，以及资源分发和品牌官方入口调查；QA 23–25 已确认混合来源、工程固定版本和小型基础库加按需下载／离线包。尚未接入 App 家具库、厂商服务、原生渲染或生产制造，产品决策与运行证据分别记录。

## 一、已经取得实际文件

从 Sweet Home 3D 官方模型页定位其 BlendSwap CC0 子集，再通过官方链接下载 `3DModels-BlendSwap-CC-0-1.9.3.zip`。本地 23,762,967 字节与官方下载页公开 SHA256 完全一致：`f87b1689df18a1b4302446dcb51922eca4d93ae9f388cf86624eb633f3068c39`。[官方子集说明](https://www.sweethome3d.com/free-3d-models/)、[固定下载与摘要](https://sourceforge.net/projects/sweethome3d/files/SweetHome3D-models/3DModels-1.9.3/3DModels-BlendSwap-CC-0-1.9.3.zip/download)。

外包 LICENSE、内层目录元数据和 175 个条目的许可字段均声明 CC0；作者与各模型目录中的许可文件继续保留。这不将同站其他 CC-BY／Free Art 素材混入 CC0 子集。

| 检查对象 | 实际结果 |
| --- | --- |
| SH3F 容器 | 24,504,042 字节；985 个 ZIP 条目，其中 809 个文件 |
| 模型 | 175 个 OBJ，分别有 MTL；含目录信息和预览图 |
| 本地模型／图标／目录尺寸 | 175 条均存在，目录尺寸为正且有限，来源身份不重复 |
| 基本引用关系 | 169 条通过本次基础检查，6 条有资源问题 |
| 问题 | 7 个作者机器绝对纹理路径、4 个缺失纹理引用，涉及 6 条目 |
| 原生导入／材质呈现 | 未验证，不能据此标为完整可用素材 |
| 参数化或制造信息 | 普通外观网格，没有完整柜体板件／五金数据 |

受影响的是两个 Bed、两个 Technical table、一个 Text marker 和一个 Chair。原始文件保持不变，问题进入条目记录；未读取作者机器路径，也未用随意同名图片替代缺失资源。首次检查因绝对纹理引用停止的记录保留；修正后的检查器将对应资源标为待修复，继续检查其他条目，没有把错误改写为“全部通过”。

当前检查不是通用 OBJ／MTL 导入器或几何有效性认证：只对固定包的已观察语法建立资源与基础网格清单；三角形数为 `n-2` 估计，未运行实际多边形三角化。整个子集累计约 130 万顶点，不能据此要求全部模型常驻场景；应先显示小预览，选用时才加载几何并按真实预算处理。

## 二、尺寸、坐标和来源不能混用

该目录的宽、深、高按官方格式定义为厘米；暂存原型保留源值并明确转换成 mm。原 OBJ 顶点包围盒另行记录，未自动当作毫米。旋转、前向和锚点保留待原生适配，不能只按扩展名猜尺度。[官方目录字段定义](https://www.sweethome3d.com/javadoc/com/eteks/sweethome3d/io/DefaultFurnitureCatalog.PropertyKey.html)。

例如第一条扶手椅的目录声明为 594 × 627 × 1050 mm，属于来源提供的名义尺寸，未作实物测量。后续原生导入应核对缩放、朝向和实际投影；摆放模型、可缩放网格与可参数化／可生产家具仍分别记录。

## 三、资料进入可检索暂存库

在既有设计 schema 中为 `search_entry` 新增了 `asset_version_id` 外键，避免资产搜索只返回一个模糊文件名。原 24 项基础数据库检查在新输出目录重新通过，8 类表单保持有效；没有修改 App 数据库或旧原型数据库。

`stage_furniture_catalog.py` 实际建立了以下数据：

- 175 个稳定资产定义、175 个版本、175 个来源位置，以及对应检索条目。
- 原包按摘要保存一份；模型通过“原包 → SH3F 成员 → OBJ 路径”定位，依赖文件保留各自摘要。未重复解压保存全部模型／纹理。
- 官方中文名称与英文原名共同检索：查询“扶手椅”找到 3 条，并能回到确定的资产版本；无效资产外键被拒绝。
- 6 条资源问题可通过结构化状态筛选；SQLite Backup API 的备份重开仍有 175 个版本。
- `asset_release` 为 0：这些是已检查的目录暂存条目，没有冒充完成原生素材入库。

此次对原包的本地存储采用同卷硬链接，无额外复制整包；这是本地研究资料的储存方式，不是 App 已完成的资源缓存服务。嵌套归档定位信息也是设计合同，App 中的解包／校验／导入服务仍待接入。

现有 FTS 使用明确词条和官方名称；“扶手椅”查询成功不表示通用中文分词、语义检索或 AI 工具调用均已完成。原型只读查询和采用操作仍应通过项目服务提供，AI 不直接执行任意 SQL。

## 六、自有资源仓库、上游更新与直接取用

用户进一步要求比较家具／家居库的存放和更新方式，并取得百隆（Blum）、萨利奇（Salice）等品牌官方铰链 CAD 与技术资料。QA 23 已确认采用**自有统一目录、可托管资源的版本包、厂家服务适配及本地离线资源**共同组成的混合方式。这是已确认的产品方案，尚未部署资源服务。

| 资源类别 | 混合方案中的存放与取得方式 | 更新与工程使用 |
| --- | --- | --- |
| Floe 自有参数配方、二维符号及有明确托管依据的基础家具 | 自有资源库提供确定版本；代码仓库保留目录、规则、许可证及构建／检查代码，模型和贴图放专用包存储 | 可跟进上游新版本；工程采用具体版本 |
| CC0 家具／PBR 材质 | 可筛选后进入自有版本包，也可经官方 API 按需取得；保留原始文件、来源、摘要和转换版本 | 新数据暂存、检查后成为新版本，旧版继续可定位 |
| 厂家允许分发的合作数据包 | 按厂家协议进入品牌专区，记录覆盖的地区、型号和版本 | 使用约定的更新方式和范围；不把合作入口当成已取得整包 |
| 仅提供用户下载或需厂家账号的资料 | 厂家官方服务／用户授权会话取得，按具体条件保存在个人或工程资源范围 | 自有目录可以记录取得路径；是否可缓存、转换、随工程交付或重新托管逐项记录 |
| 用户导入、定制家具及 AI 创建资产 | 默认属于用户的个人／项目库，保留导入来源与生成依据 | 生成新版本；加入公共资源库是另一个明确操作 |

这里的“进自己仓库”建议落实为受控的资源库，而不是把全部厂家原始文件塞进 App 源码 Git。目录、适配代码、合法的模板和许可记录适合 Git；大模型、纹理及版本包由专用存储承载。具体托管位置沿用项目现有资源基础设施，不在预研阶段另行部署服务器或发布仓库。

Poly Haven 官方明确允许其 CC0 资产再分发，但实时 API 另有规则：当前允许免费商业使用，应用调用需有可识别的 User-Agent 或 Referer，并展示来源。网站抓取与公开 API 不应混用。ambientCG 的资产及预览许可同为 CC0。[Poly Haven 资产许可](https://polyhaven.com/license)、[实时 API 条款](https://github.com/Poly-Haven/Public-API/blob/master/ToS.md)、[ambientCG 许可](https://docs.ambientcg.com/license/)。这只是这些明确来源的事实，不能推广到所有家具站或品牌文件。

## 八、品牌零件不是只登记一个模型文件

每条品牌数据至少要能关联：品牌、系列、明确订货型号、表面处理／左右件等变体、适用市场、目录版次、来源及取得时间、文件摘要、表示格式、单位与安装基准，以及已知兼容底座／附件。三维几何、二维安装图、说明书、运动包络与孔位／选型规则分别记录，缺失字段保持未知。

Salice 实际钻孔样本第 2 页区分螺钉、木榫、Rapido 和 Logica 固定方式；第 3 页把开门间隙与门厚、钻孔边距及门边圆角等条件关联。因此同系列外观接近的铰链不能共用一条未经限定的钻孔规则，型号、固定方式、底座及适用条件需要共同绑定。该样本是美国版资料，不自动视为其他地区同型号的当前依据。

原始厂家资料 → 带页码／图示范围的候选参数 → 经核对的型号／安装规则版本 → 柜体实例中的五金配置 → 安装图、孔位图和清单。AI 可帮助整理与定位依据，缺少依据时保留待补项；当前没有将这些样本文档转成已验证制造规则。

## 九、同步与离线工作设计

已确认混合方案对应的拟议实现流程为：

```mermaid
flowchart LR
  A[官方目录或数据服务] --> B[来源适配与更新检测]
  B --> C[新版本暂存与检查]
  C --> D[自有统一目录]
  D --> E[允许托管的资源版本包]
  D --> F[厂家取用入口]
  E --> G[本机按需下载或离线库]
  F --> G
  G --> H[工程固定的资产与规则版本]
```

同步先保存原始数据和来源，再做依赖、尺寸／坐标和格式检查。新版本与旧版本并存；目录校验通过不等于原生导入、五金运动、孔位或制造验证通过。复用现有资源下载、任务、取消及原子保存服务，不把长下载绑在视图生命周期上。

按 QA 24，工程引用固定资产版本、文件摘要、安装配置与制造规则版本，保留升级前后的对应。新库可以持续取得更新，已有工程由用户主动决定何时采用新版；发现新版本身不修改原工程。本轮只确认策略，没有启用运行中的自动更新任务。

工程升级设计分为以下步骤，均需后续实施验证：

1. 固定当前工程版本、已采用资源及依赖；取得待采用的新版本，先检查其可用性和适用条件。
2. 比较型号／变体／地区、几何尺寸与安装基准、材质与纹理、兼容附件、安装／孔位规则及依赖。仅名称相同不能认定等价；结果列出受影响的部件、图纸、标注与清单。
3. 用户选择采用范围后，生成可撤销的升级修订；按原有稳定部件身份更新关联成果，保留人工说明和排版。失去关联的对象明确进入待修复状态。
4. 采用过程使用可恢复的项目提交机制。失败、取消或工程同时发生修改时保留原版本；CAD 原件与资料库之间的联合保存仍是待实现、待验证的合同，不能把一次数据库提交视为两者已经原子一致。

按 QA 25，默认提供小型基础库并按需下载，用户可选择指定素材库作为离线包。离线状态应从目录可见、下载中／中断、依赖待补，区分到文件与依赖已取得的实际可用状态。下载有进度、取消和失败恢复；缺少文件或条件的条目不能以成功状态占位。

工程采用的资源及依赖、显式下载的离线包、可清理的临时缓存分别保留引用关系。删除离线包或清理普通缓存时，仍被工程使用的确定版本继续保留。资源版本升级不会顺带删除旧版本；后续清理依据真实引用和可恢复性处理。厂家资源能否进入离线包或随工程交付仍按来源条件记录。

本轮新增证据位于 `interior-component-research-20261112/brand-library-research01/`，包括实际页面、文件摘要、三份官方 PDF、PDF 信息和已查看的页面渲染。它们是本地研究证据；没有作为可再分发的成品素材包发布。`asset-sources-v0.json` 同步登记品牌入口与本轮建议，不改变 SQL schema 或此前数据库检查的验收范围。
