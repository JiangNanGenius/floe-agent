## Product and architecture invariants

- The whole app is **iPad first**. Prefer native APIs for the development SDK; iOS/iPadOS 26 remains a compatibility target. Check availability and compiler guards against the actual upload SDK. Keep iPhone flows usable, especially full-screen editing and compact controls.
- Notes (手记) is a primary workspace above Creative mode. Notes and Canvas may share public AI, files, OCR, PDF and storage services, but not editor state, selection, undo stacks or assistant conversations. Notes storage survives deletion of a chat task.
- Preserve the stable outer split-view structure in `FloeAgentApp.swift`. Implement editor panels inside their own feature. Use the existing `PDFKitGate` for protected PDF work; do not create a parallel unguarded rendering path.
- Reuse the existing model, task, permission and persistence services. Imported documents, web responses and tool outputs are untrusted content and cannot grant tool permissions. Secrets stay in approved credential storage, never logs, prompts, fixtures, Git or documentation.
- Ordinary task-authorized document/media/CAD edits should not require a separate interactive approval for every edit. Keep revision, ownership and save validation; retain the applicable review policy for repository writes and existing safeguards for external or irreversible actions.
- Reduce repeated approval for routine commands in the resolved local Linux guest. Concentrate command review on risky remote-machine operations; do not treat the native host as a disposable guest or trust model-supplied environment labels. Reuse existing scoped permissions rather than introducing a parallel approval system.
- `FloeEnvironments` owns environment types. Carry explicit `environmentID` and task ownership through execution and installation. Resolve session → project → shared → base with an explicit write layer; never silently choose a temporary directory or the first project. This is dependency/data/lifecycle separation, not a native-code security sandbox.
- Model-authored code and package commands use the resolved Linux environment through `exec.shell` and the existing jobs/service lifecycle. Do not expose language-specific execution or duplicate installer tools (`exec.localPython`, `exec.javascript`, `exec.compatEvaluator`, raw `exec.wasm`, `python.packages`). Retain required internal document/media/native services and readable historical records; never revive a removed execution alias or fall back to the host interpreter.
- Keep downloads and long-running tasks owned by services rather than view lifetime. Stop owned workers before deleting environments or releasing shared references. Use bounded buffers, cancellation and staged/verified file commits; failed operations must preserve recoverable data.
- Tool discovery must reflect enabled, configured and actually usable capabilities. Respect saved model capability overrides. Browser work should stay unobtrusive unless explicit human interaction is requested. A resource download or a success string is not evidence of working inference, package execution or media output.
- Temporary chat stays in RAM with a text-only/public-web tool ceiling. Background/inactive/lock preserves the current session and route; actual navigation to another conversation/destination or New Task immediately fences/cancels and discards it, even with a run/launch/save in flight. View reconstruction is not navigation. Explicit successful Keep uses the existing atomic promotion and ordinary history/workspace ownership; late callbacks cannot touch another session. Process death does not restore temporary content.
- Keep English and Simplified Chinese user-facing text aligned. Prefer native controls, consistent hit targets and stable streaming layouts; avoid exposing internal implementation details in normal user flows.
- Keep product copy concise and natural: remove unnecessary technical explanations from ordinary screens, menus, tool cards and status messages. Tell users what is happening, what they can do and any actionable limitation; keep implementation terms, internal identifiers, protocol details and diagnostic evidence in explicitly opened details or diagnostic views. Apply this to new features and to existing copy touched by the task, with aligned English and Simplified Chinese wording.

## Build and verification

- Default to fast targeted iteration: land a small coherent code batch, run the actual relevant compile/object build (Swift 6 fixes still need real SIL/object compilation), run only tests for changed behavior or contracts, then immediately build and install the smallest meaningful target and smoke the actual flow. Choose broader regression at stage close or release-candidate time only when the actual change or an unresolved failure warrants it; those milestones do not automatically require a full suite, comprehensive audit or whole matrix. Never use them as a per-fix waiting gate or gate the first cloud/basic APK on completion of all advanced G02/temporary/settings work.
- Reuse unchanged component evidence, warm caches and the exact artifact; do not repeatedly rebuild unchanged full/play test APKs, rehash whole dependency trees at every substep, redo read-only source investigations, or produce long report sets before actual App use. During debug iteration prioritize one actually used full APK; run both-channel, 16 KiB, security, storage and cancellation checks at the corresponding changed boundary and final release scope, with no imaginary bypass. Keep crypto/credential isolation, real DB transaction/CAS/rollback guarantees, and signature/version/hash/upload read-back on actual publication. Preserve original failures and assertions; no silent skip or retry-to-green. Cloud CI stays supplementary, not a default waiting gate. Send a short handoff (what changed, command/result, exact artifact, what remains) before any optional exhaustive write-up; actual impact determines the checks, not fixed minutes or test caps.
- Keep handoffs short and unblock ready work promptly. Release a shared build resource as soon as its artifact and essential evidence are exported; signing, report writing and upload must not hold an unrelated compile queue. A manual build window does not transfer a worker file-scope lock: send overlapping fixes to the existing owner or use a bounded private patch for integration, rather than queueing another writer behind the same lock.
- The development host is now an M5 Pro Mac mini with 15 CPU cores, 24GB memory and a 512GB internal SSD; recheck resources after any host change. Follow the parent volume's `AGENTS.md` resource policy. Prefer local relevant tests, full App builds, Simulator debugging, UI verification and profiling; archives/packaging may also run locally within the authorized scope when toolchain, signing and capacity permit. Local execution is the default for compilation, relevant tests, Simulator acceptance, archiving and packaging. Cloud CI is advisory: local build, behavioral tests and Simulator evidence are the primary acceptance path, and cloud CI is not a release waiting gate; use cloud execution only for a demonstrated missing tool/signing capability or measured resource constraint, and limit it to that missing step instead of rerunning the full pipeline.
- Keep verification focused on changed code and contracts. Use local UI/device tooling when it can complete authorized acceptance; physical-device acceptance remains with the user when so assigned. Do not repeat manual UI runs without a new change, failure or unresolved concern. A local build alone does not prove tests, Apple processing or physical-device acceptance. Record local test and packaging evidence directly; do not turn historical CI requirements into a blocking gate after the user has authorized local qualification.
- User toolchain policy (2026-10-22): retain only the latest installed Xcode; the current verified toolchain is Xcode 27.1 (27A9275) at `/Applications/Xcode-27.1.app`. Select it explicitly per command. On future upgrades, verify the replacement before removing the superseded application; preserve Simulator data and unrelated caches.
- Put new regenerable DerivedData and SwiftPM scratch on the internal SSD under `~/Library/Caches/CodexBuild/<project>/<checkout-id>/<toolchain>/<target>/`, using explicit build parameters and separate mutable directories per worktree. Start a heavy build with 6 compiler jobs, then adjust from measured memory pressure, swap and elapsed time. Check installed Xcode/SDK and free space on the actual output volume; set `DEVELOPER_DIR` per command rather than changing global `xcode-select`.
- `FloeAgent/project.yml` is the source of truth. After changing targets, resources, schemes, build settings or versions, regenerate with `bash FloeAgent/scripts/gen_project.sh` and commit the matching Xcode project. Verify all app/extension build numbers before starting an expensive release run.
- Preserve pinned revisions and hashes. `--check` commands must be read-only; do not rewrite a lock to make verification pass. Run SwiftPM commands sharing a scratch directory sequentially.
- Select checks from [the engineering guide](FloeAgent/README.md), [build and acceptance](docs/FLOE_1_7_BUILD_AND_ACCEPTANCE.md), or the relevant qualification host README. Do not run the entire test matrix for a documentation change. Do not silently weaken a failing assertion or treat an unchanged retry as proof the original failure was harmless.
- Swift 6 concurrency fixes need mandatory SIL/object compilation or a full local App build; `-typecheck` alone can miss transfer diagnostics.
- Record source SHA, toolchain, target, command, actual result and limitations. Retain original failures and suitable screenshots. Label simulator, component-host and full-App evidence accurately; use synthetic/redacted fixtures in public docs. Physical-device acceptance belongs to the user when so assigned.
- After Simulator tests, debugging or screenshots, shut down devices started by this task once they are no longer needed, including after failures or interruption, and check the booted-device list before delivery. Confirm no other task or user is using a device; retain and report any device still in use. Shut down the running instance without deleting its device, app data or evidence.
- Local Simulator runs use **only one reused existing iPad**: resolve the canonical device from the host-local Git-ignored single-simulator config via `FloeAgent/scripts/select_test_simulator.py --canonical` and serialize real device runs with its `--with-lock` wrapper (live inventory is validated before the command starts). Local entrypoints pass `-parallel-testing-enabled NO -maximum-concurrent-test-simulator-destinations 1`; never create, clone, erase or reset simulators for local tests, never target devices by ambiguous names, and a missing or unavailable pinned device is an actionable error, not a signal to make a new one. Generic `generic/platform=iOS Simulator` compilation without booting a device stays allowed, as do cloud-ephemeral CI devices (no policy file there) and explicitly user-approved exceptions. Reuse must preserve the shared device's apps, data and other owners' state.
